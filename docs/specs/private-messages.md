# 私信运营契约

正文篇幅与独立运营生成额度沿用[运营正文契约](comment-operations.md)，不采用直播台词120字或角色style长度作为私信硬限。channel_max_tokens用于首次主动联系的来源核对等小结构，与正文额度分别计量；普通来信回复不增加这次核对。

渠道及正文生成的具体反馈、检查点、平台拒绝修订与未知发送核对沿[运营任务继续契约](operation-continuations.md)；原收件人、来源与私域边界继续由本规范维护。模型可与评论任务一样按需选择公开HTTPS页面，不要求来信先附链接；材料足够时直接回复。网页工具仍为单页、3秒取材及有限摘录，直播不接入该工具链。

私信是自主运营内的私密工作区，与评论、动态共用账号配置、角色版本和模型调度；不通过直播队列或TTS输出。真实平台能力与发送权限须另做账号验收，隔离传输测试不代表真实私信已经发送。

| ID | 要求 |

## 联系依据与发送状态

| 实际来源 | 行为 |
| --- | --- |
| 对方发来新私信 | 合并同人连续消息，自动决定回应内容。 |
| 对方在评论中邀请大肥鱼私聊 | 按作者、父评论及真实 @ UID 确定受邀者，自动首发并接原话题。 |
| “查到了私信告诉我”等约定 | 保留来源、目的和同一草稿；真实工具或任务完成证据回绑约定后联系一次。未完成不发送，不用模型自称完成作证。 |
| 普通提问、聊天，或 @ 自己的 OC／其他人 | 按原讨论公开接话，不因此开启私聊。昵称相似不算账号相同。 |
| 曾经聊过但无新来信、无约定 | 不主动找人。 |
| 我方已发、对方未回应 | 等待；同一事由跨入口合并，不追问或重发。 |

主动联系记录 `purpose`、真实 `trigger_source`、首发核对结果及发送状态。有效依据与具体交流内容必须能回绑原文，语义判断不要求固定关键词。首次指每次开启新的主动交流，不是某用户一生只核对一次。原模型行动与正文可复用，核对不再重复生成一份首发。

评论行动选择前复用同一份原始候选和UID关系判断是否可能存在邀请：只有资料完整且机械上不可能邀请我方时，才移除私信行动，避免反复创建必定不合格的私信草稿和额外核对请求。资料缺失仍保留原核对路径，不视为获得发送依据；同一收件人在较早楼内的真实邀请仍能使用。公开旁观参与、正常来信回复和真实约定不受影响。

模型提议的“约定”也必须先核对原文、受邀UID与实际回复关系；`wait` 不豁免核对。只有真实约定可保存为等待完成并启动后续取材任务，普通评论或面向其他账号的邀请进入 `not_initiated`。旧记录只有程序等待说明而没有邀请核对结果时，不启动约定任务、工具完成唤醒或重试。真正的完成回执回来后，仍核对即将发送的实际结果，不能复用完成前的候选正文。

`not_initiated` 表示没有取得主动联系依据，进入历史；`waiting` 明确区分等待约定完成、等待对方回应或等待有效邀请，不等于待人工审核。旧待发候选同样重新核对，旧理由不能直接获得发送资格。界面区分“回复来信”和“主动私信”，显示触发来源、联系目的与原回执；公开活动不展示私信正文。

审核模式同样执行主动联系依据核对。首发核对完成前保留生成中状态，不能提前进入待审核或发送；核对期间出现新来信、拒绝或编辑时，旧核对结果不能覆盖新状态。只有核对通过的候选进入待审核；普通新来信回复保持原来的轻量路径。

专门的 review 验收会话在 `starting/running` 期间阻止该账号的自动及手工平台写入；私信发送入口在刷新身份、生成或图片上传前检查同一写入限制。旧已审核稿不能借手工接口出站，未知回执仍允许只读核对。会话明确停止后解除这一临时限制，历史验收元数据本身不会永久封锁发送；自动发送权限仍按保存的设置执行。

当前平台适配接账号范围内的文本或单图片私信，图片来源与选择由[表情包规范](memes.md)维护。图片先上传准备，最终只发一条type=2消息，不自动补发原文字；只有最终提交才预约防重复意图。上传明确失败保留草稿可人工重试，最终提交结果不确定仍不可重发。仅使用固定HTTPS地址和现有登录凭证；不自动解决平台验证，不因可读推断可写。收信先确认登录UID，只导入属于该账号、来自该会话用户的正常文本；忽略本人、群组、撤回、系统或其他收件人的消息，不调用已读接口。最近20个会话、每会话30条是本轮读取上界，不声称已读完整历史。

评论转私信后，公开草稿只显示移交标记，不能当作公开回复审核或发布。私信草稿保留来源评论ID和用户身份；在运营内的私信页审核、修改、拒绝、复制、发送或重试未发送的生成失败。模型没有修改收件人、关系值或直接调用发送工具的权限。更换账号后，旧来信不能被新账号代为回复。视频评论和通知评论共用真实来源移交路径，模型选择须保留原始具体解释，并落到实际私信联系记录；程序移交状态单独保存，不覆盖“大肥鱼判断”。

工作台在页内区分待处理与历史；发送、拒绝或持久复制成功后移出待处理并清空详情，失败保留正文。切换会话时立即清除旧来信和关系展示，迟到响应不能覆盖当前选择；未保存编辑按草稿保留，回来可继续。

关系基线为好感度20，支持骑马与砍杀战团式双向区间 [-100, 100]；阶段划分为：宿敌(<= -60)、恶感(<= -20)、陌生(< 30)、认识(< 60)、熟悉(< 90)、特别熟悉(>= 90)。厌恶区间（-100至-10）以幽默辛辣回怼与冷淡防卫为主，严重违规拉黑；普通观众弹幕走内存LRU，仅在付费打赏、深层互动或|好感|>=10时持久化落库。评论和私信共用同一条关系及增量账本，模型不能接受观众指定数值；匿名用户不建立长期关系。

### 号主手动回复识别与协同接话 (Human Takeover Co-pilot)
- 历史拉取时区分系统发送回执与号主在平台网页/APP上的手动回复（`dm_operator_replies`）。
- 当检测到号主已在平台手动回复用户时，系统自动取消/标记该用户处于待发状态的旧生成草稿（`status='cancelled'`, `error='号主已在平台手动回复，无需重复发送'`），杜绝机械重复发信。
- 用户产生新追问或会话继续时，号主手动回复作为 `[号主/饲养员回复]` 汇入会话上下文与协同指导语，大肥鱼自然接力跟进，不重复号主已说明的要点。

私信收件、发送草稿／回执与关系账本持久保存在本地数据库，与媒体缓存分开。模型活动窗口及来源检索索引沿用对话留存；原始私信和发送审计不因媒体清理或窗口到期被删除。这与原始评论、草稿和回执的独立保留方式一致。

收件／草稿身份、关系和私密scope包含当前已核验账号。同一账号内公私渠道共享关系；切账号不展示或继承旧账号私密窗口。旧无账号记录保留在旧范围，不自动认领给新账号。视频移交持有公开证据引用；父轮取消会收齐其未提交生成，压缩、修复和思考tokens均计入实际用量；自动批次不据此增加隐藏累计上限。直接私信仅在正文含受支持视频标识或延续该用户已关联话题时重读视频材料。

未提交的排队／生成任务在停止、网络失败和重启后保留为可恢复队列。服务冷启动待命，用户明确开始自主运营且已保存对应私信权限后，再按当前账号与OC范围少量补入恢复任务，给新来信留出位置。恢复按当前保存的自动／手工授权执行，不继承已经撤销的发送授权，也不恢复已归档的旧人设生成。有效新来信与真实邀请无需重新逐条审核；依据不足的主动联系等待或不发起。发送中断仍只核对原提交，已生成草稿与回执独立留存。

验收覆盖：新来信合并→自动回复→单次发送回执；真实我方邀请／第三方邀请分流、约定完成一次联系、同事由未回应不再联系；任意收件人字段拒绝；历史不追发；停止、取消和重启不重发；同昵称不同UID／不同OC隔离，同UID跨渠道共享数值；私信不进入公开素材；无凭证、平台拒绝和不确定结果可见。真实模型的渠道选择与真实平台的发送能力分别验收。

缓存与收发路径、渠道质量及真实账号的证据与验收状态见[当前计划](../plans/current.md#运营主线)。
