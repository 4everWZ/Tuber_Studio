# Q 成图：两个既有 90 秒窗的离线分解

仅复读[四窗验收](approved-oc-whep-windows-20261119.md)中 Q 的两份归档。没有重放通话、请求网关或改播放器。这里的“同订阅段”是同一个接收 Peer 首、末观测呈现时标之间的墙钟区间，**包含段内卡顿**；“跨订阅间隙”从旧段末帧至新段首帧，不把整段间隙归因给信令。

| 90 秒的组成 | 单通话 | 并发 Responses |
|---|---:|---:|
| 同订阅段总跨度 | 85.908 s（2 段） | 78.660 s（4 段） |
| 跨订阅无呈现回调的间隙 | 4.091 s（1 次） | 11.272 s（3.788、3.642、3.842 s） |
| 末帧至窗末 | 0.002 s | 0.068 s |
| 同订阅段合计呈现率 | 22.26 FPS | 21.51 FPS |
| 全窗实际呈现 / 目标 2250 帧 | 1914 / 2250 | 1696 / 2250 |
| 按 25 FPS 折算的总缺口 | 13.440 s | 22.160 s |
| 其中同订阅段净缺口 | 9.428 s（70%） | 10.980 s（50%） |
| 余下的跨段及窗界净缺口 | 4.012 s（30%） | 11.180 s（50%） |

计算取 `frames.json` 的期望显示时间、Peer 编号及累计呈现帧数。每个同订阅段用“末计数减首计数”除以同一段的末首时差，按时长合并，不取逐段 FPS 的算术平均。净缺口是同一跨度减去计数差除以 25；总缺口是 90 秒减去全窗帧数除以 25。跨段净额含各段首帧与窗尾的边界校正，不等于跨段毛间隙。冻结统计可能与这些时间重合，不再相加。

**25 FPS 的证据。** 单通话主要损失在同订阅段；并发两类损失接近各半。按同一视频 SSRC 取首末有效 connected、640×720 的 `stats.json` 样本：单通话第二段 73.02 s 内解码增加 1820，呈现增加 1655（24.92 对 22.66 FPS），浏览器 dropped 计数只增加 2。并发第二段 32.01 s 内为 795 对 684（24.84 对 21.37 FPS），dropped 增量为 0。对六个接收 WebM 逐帧读视频 PTS，文件帧率为 24.84–24.97 FPS。文件编码、接收解码、送交呈现是不同计数；不能将其差额当作某个队列的精确丢帧数。证据支持“接收流接近 25，但页面呈现未维持 25”，不能据此区分网络晚到、解码突发、浏览器排程或渲染压力，更不能把两窗差异归因给 Responses。

**160 ms 的证据。** 以下“剔除首尾”只定位问题，原准入结果不剔除任何样本。时差是视频 RTP 相对音频 RTP，负值为视频时间落后，不是听见语音到嘴动的物理延时。

| 同一 SSRC 内的样本 | 单通话 | 并发 |
|---|---:|---:|
| 全窗超限 / 有效配对 | 56 / 1885 | 13 / 1680 |
| 各段首尾各去 5 s 后超限 / 剩余配对 | 44 / 1478 | 10 / 824 |
| 剔除前后最大绝对偏差 | 360 → 360 ms | 260 → 260 ms |
| 不依赖发送首包常数的绝对峰值下界，剔除后 | ≥300 ms | ≥200 ms |

单通话窗第 66.382 s（换订阅后 51.056 s），两次呈现回调相隔 309.1 ms，视频 RTP 只进 40 ms，配对音频 RTP 进 320 ms，偏差从 −80 变为 −360 ms。并发窗第 21.368 s（换订阅后 6.266 s），回调相隔 284.9 ms，视频进 40 ms、音频进 300 ms，从 0 变为 −260 ms。最大值发生在同订阅的呈现停顿处，不在换订阅间隙中；间隙本身没帧可配，不能断言其间同步良好。单通话 56 个超限样本中 30 正、26 负，并发 13 个均为负，不能用一个固定唇音偏移概括。

发送侧探针捕获队列有丢包，故绝对值取各轨首个**观察到的**发包为锚。但同一订阅内加未知常数不改变时差全距：剔除首尾后，同一段仍分别有 600、400 ms 全距，至少有一个绝对偏差达到其一半。两个窗的 RTP 采样指标均超限，不能靠调整起点或删除换订阅过渡变成合格。音频同步源采样不是扬声器实播时钟，归档不足以将这些峰值直接判为同等大小的真实口型延迟。

**可复现的测量问题，归属验收探针。** 对齐 `interrupts.json` 点击时间、`levels.json` 首个新编号且 playing 的轮询和 `frames.json` 新段首呈现回调：

| 点击 → 对应观测 | 单通话 | 并发 1 / 2 / 3 |
|---|---:|---:|
| 当前 `new_peer_play_ms` 判定 | 1.191 s | 0.862 / 0.692 / 0.739 s |
| 新订阅首个观测呈现帧 | 4.086 s | 3.785 / 3.640 / 3.840 s |

采集版本 `31fe82d` 中，状态的 segment 取最新构造的 Peer 编号，playing 仅检查 video 有流、未暂停、未静音；逐秒网络统计却来自最近触发 playing 事件的 Peer。例如单通话点击后 1.810 s，逐秒样本已标为 segment 2，但采样对象仍报 closed，视频宽为 0，呈现计数仍是 222。不能把这行归为新 Peer 的连接失败，也不能把前述布尔判定称为新画面已恢复。

建议由验收探针维护者分开记录“新 Peer 创建”“元素挂流”“同一 Peer/track 的首个呈现回调”。统计记录携带实际被查询的 Peer 编号和 SSRC；没有新帧就保留缺测。未改共享代码。存量记录可纠正恢复时标；不足以证明播放器必然多等三秒，也不足以判定 ICE、重订阅 API 或驱动有对应缺陷。
