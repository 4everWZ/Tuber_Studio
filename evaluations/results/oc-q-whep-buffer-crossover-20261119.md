# Q 原画同一链路的双轨缓冲对照

在这条工作站到桌面的线路上，双轨 240 ms 显著减少了冻结，也增加了收端播放等待。四个完整的 90 秒窗均未达到原 25 FPS、零冻结、音画相对偏差不超过 160 ms 的准入条件。

| 受控窗 | 全窗实呈 FPS | 冻结次数 / 总秒数 | 最大绝对 RTP 偏差 ms | 超 160 ms / 有效配对 | 实际缓冲音 / 视频 ms | 视频末包到呈现中位 ms | RTT 中位 ms / 有重传的视频时戳占比 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 自动 A1 | 14.50 | 72 / 23.52 | 380 | 41 / 1299 | 32.8 / 93.9 | 58.4 | 187 / 24.7% |
| 240 ms B1 | 21.23 | 3 / 0.77 | 260 | 2 / 1909 | 203.7 / 223.8 | 246.4 | 182 / 36.3% |
| 240 ms B2 | 19.73 | 7 / 1.83 | 400 | 5 / 1769 | 196.0 / 226.5 | 244.0 | 183 / 34.5% |
| 自动 A2 | 14.17 | 98 / 24.59 | 520 | 177 / 1194 | 109.4 / 142.9 | 84.3 | 184 / 31.5% |

两次 240 ms 场的同 Peer 段内呈现率分别为 24.30、23.73 FPS，跨订阅及窗界空白分别占 11.52、15.31 秒。这些空白仍计入全窗分母。B1、B2 最大偏差分别落在本段首个有效配对后 3.41 和 13.74 秒；即使只看段内，仍可观察到超限。偏差按各 SSRC 工作站首发 RTP 归零，比较视频呈现帧与最近音频同步源。

| 受控窗 | 开始按钮 → 首帧 / 首音 s | 三次打断 → 旧元素停播或检测静音 ms | 三次打断 → 新轨首个呈现帧 s | 三次打断 → 新轨首音 s |

| 240 ms B1 | 5.99 / 16.61 | 10、15、15 | 3.82、3.67、3.96 | 17.79、16.73、18.57 |
| 240 ms B2 | 8.30 / 18.68 | 7、9、11 | 4.58、5.18、5.42 | 17.22、24.39、17.91 |
| 自动 A2 | 6.95 / 17.39 | 18、11、8 | 3.66、4.03、3.82 | 18.89、6.70、18.22 |

首帧取绑定到对应 Peer 和视频轨的首次呈现回调的预计显示时刻。首音取播放器有绑定、正在播放、未静音时，接收音轨首次 RMS > 0.004 的浏览器采样。另解码各段双轨 WebM 核对非静音信号。采样周期约 20 ms，停播栏给出下次观测时刻；未测物理扬声器的尾音。所有完整窗口的十二次打断在 350 ms 检查点均已静音或停播。打断后的新轨首音包含等候下一次模型输出，启动首音还包含测试麦克风的 6 秒前置静音。两项都按真实等待计时。

配对看 A1 → B1 与 A2 → B2，240 ms 的视频末包到呈现中位等待分别增加 188.0、159.7 ms；音频实际平均缓冲分别增加 170.9、86.6 ms。这个播放代价在两对里方向一致。冷启动首帧与首音则一对更早、一对更晚。保持浏览器自适应为默认，240 ms 适合作为用户可选的减少卡顿控制。

## 复测条件

桌面 Chromium 登录工作站 9443 隔离 Studio，经正式网关和 Inochi worker，以同一 Q 原画、640×720、25 FPS 发送目标、VP8/Opus 和同一段话音输入运行。只在验收浏览器创建接收器时请求 240 ms，覆盖首个订阅与所有重订阅；自动组使用浏览器原值。逐轨保存目标回读，实际平均缓冲由同一 SSRC 的 jitterBufferDelay 增量除以 jitterBufferEmittedCount 增量，再按实际发出样本数加权。视频末包到呈现取同一已呈现帧的浏览器 receiveTime 与 expectedDisplayTime 之差。网络质量随时间变化，每种设置两次，不以单次冷启动差值推算缓冲延迟。

按自动、240、240、自动顺序串行完成四个有发送锚点的窗口。首次 240 ms 尝试在挂断后的包头文件传输阶段超时，保留原始收端记录并补测 B1。该额外窗口为 21.26 FPS、1 次冻结 / 0.28 秒，首帧 8.48 秒、首音 18.93 秒，视频末包到呈现中位 249.6 ms；缺少发送锚点，音画偏差缺测。补测只压缩了测后传回的诊断文件。
