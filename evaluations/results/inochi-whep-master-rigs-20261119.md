# 工作站两套原画的 WHEP 浏览器实测

两套形象均使用工坊正式目录 `runtime/releases/dafeiyu-avatar/master-rigs/{regular,q}/model.inp`，每套 13 个 PNG 部件。以下记录来自 640×720、25 Hz 的 Inochi2D CPU 渲染与真实 Chromium 接收。独立服务提交为 `69ee013`。两套绑定及统一测试句的制作见[原画记录](original-avatar-rigs-20261119.md)。

## 浏览器与计数

媒体服务与 Brave Chromium 156.0.8078.80 各占一个独立容器，位于同一工作站的专用 Docker bridge。媒体进程与浏览器各限三颗不同的逻辑 CPU，无 GPU。浏览器以 WebRTC 接收 VP8/Opus，将收到的双轨用 MediaRecorder 保存，再按原帧时标生成 H.264/AAC 播放副本。Studio 私聊入口另在 Windows Chromium 运行过两套真实绑定，语音引擎使用受控输入，两套分别收到 331 ms 和 396 ms 已播回执，打断后重新订阅，共四次成功订阅。[Studio 入口独立回归](private-rig-memory-20261119.md)

FPS 取首末入站统计时标之间播放器总帧数减丢帧数的增量。独立记录工作线程绘制、RTP 接收完整帧、视频解码和播放器呈现四组计数。无预热裁剪、断线重连、补帧或多次试验取最高值。每 11 秒交替排入 9.117 秒中文测试句和 4.2 秒角色原声，每第三次发话期间清空、读回代次，并以旧代次再次提交以检查拒绝。每约 15 秒另以普通客户端真实提交 Responses 并按 ID 核对答案。表中计数来自同一完整计时窗口。

常规和 Q 首轮均无丢包、无冻结、无超 40 ms 的绘制。常规单帧绘制 p50/p95 为 13.89/15.38 ms，最大 17.53 ms；Q 为 13.98/14.41 ms，最大 20.18 ms。Q 在第 15 秒由收到即解码转为解码计数落后一帧，直到窗末一直维持这个差。每份接收端 WebM 在自身时间轴的头 90 秒都可解码 2250 帧。播放器计数单独保留。每次均有三次正在发声的打断，三次旧音频提交全部返回 HTTP 400。打断后 350 ms 的浏览器分析窗读到静音。

音视频时钟取每次视频呈现回调上的视频 RTP 与最近音频同步源 RTP，以首个实际发送包的时间戳为共同会话起点，时基分别为 90 kHz 和 48 kHz。90 秒常规与 Q 分别取得 2250、2245 组。这个量描述收端采样的媒体时钟；下面的口唇结果另外从声轨和图像测得。[WebRTC 同步源](https://www.w3.org/TR/webrtc/#dom-rtcrtpreceiver-getsynchronizationsources)

私网长跑有 110 次交替排音、36 次打断与旧代次拒绝，全程无丢包与冻结。1199.999 秒内得到 29999 对窗内时钟样本，原始最大绝对时差 60 ms，按音频同步源时间投影到视频期望呈现时刻后为 54.30 ms。接收录屏在自身时标头 1200 秒内解码到 30000 帧，最长帧间隔 55 ms。工作线程 p50/p95/最大绘制为 13.99/14.46/20.59 ms。服务平均使用 0.493 核，cgroup 峰值 352.6 MiB、134 个线程。浏览器和记录器平均使用 0.166 核，峰值 948.5 MiB；其文件页缓存从 256.3 增至 620.7 MiB，匿名内存从 238.0 增至 283.3 MiB。两组均无 CPU 限流或 PID 配额拒绝。

再以同一网络测试把同一时标的画面提前一帧准备、仍在约定的时刻交给编码器；代次变化时重新取音。两个独立 90 秒均呈现 2250 帧，最大采样 RTP 时差都变成 60 ms。该私有对照未合入服务。跨机路径的网络瓶颈独立实测。

## 首音、闭唇与元音

从播放副本 5 ms RMS 音频包络与原输入交叉相关取得每次发话时标。首音取连续 10 ms 的归一化 RMS 超过 0.012，首次明显张口取同一录屏原始画面嘴部连通色块达到 120 px。25 FPS 图像只有约 40 ms 的时间分辨率。常规首音 0.335 s、开口 0.318 s，Q 首音 0.325 s、开口 0.278 s。六次完整句的首次开口相对出声分别领先 17–40 ms、19–47 ms。六句中，按整句开口面积与响度相关求得的最佳时移分别为画面领先 55–65 ms、45–70 ms。这两种测量分别回答起始动作和持续节奏的问题。

两套实际录像均能出现闭唇细线、较圆和较宽的开口。用同一桌面 TTS 音色重新合成相同中文句，并读取其 16 kHz 音频上的口型事件；重合成与原输入的 5 ms 包络相关为 0.993。每套检查三个完整测试句，每句八个时长至少 40 ms 的双唇音。以 9.6–10.6 s 静音画面的口内色块最大值加 4 px 为近闭唇阈值，常规和 Q 分别为 24、12 px。在目标时窗内出现过近闭唇的分别为 17/24、18/24；在目标中点正在闭唇的均为 7/24。两版在第二个“慢”字中点仍明显张开。对口内色块面积相差不超过 10% 的样本一对一匹配，展唇口型比圆唇更宽的常规为 1/7 对，Q 为 4/9 对。当前 PCM 能量与频谱亮度驱动可表现停顿与开合，未达到连续句逐音口型吻合。每个目标的实际图像 PTS 和面积均保存在私有结果中。[微软口型编号](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-speech-synthesis-viseme)

## 历次试验与本机工件

采用相同全窗输入和读回的前一轮主机网络 90 秒录像中，常规收到并呈现 2125 帧，音视频在约 85 秒停止；Q 收到 2250 帧、呈现 2247 帧。各完成 6 次独立 Responses 核对。该网络下 20 分钟试验的解码计数最后在第 271 秒变化，末次 DTLS 发送失败时会话仍可查询。独立推理成功不能作为媒体存活证据。更早一轮录像写入程序截错含逗号的 MIME 头，已排除其文件；后续写入检查首块 WebM 签名、每块字节数及最终解码。首轮渲染资源限制曾实际触发 PID 上限，改用有限 CPU 亲和性和 384 PID 上限后，私网 90 秒的拒绝和 CPU 限流增量均为零。

可播放工件与机器索引位于本机私有目录 `runtime/releases/dafeiyu-avatar/whep-validation/`。打开 `index.json` 可取每个录像的相对路径、SHA-256、统计窗、帧数、时钟差和资源曲线。两份 `whep-90s.mp4` 均通过全文件音视频解码，以及另一个 Windows Chromium 的开头、中间和近尾部播放。逐秒接收统计、250 ms 的两个 cgroup 资源曲线、每帧嘴部测量、同步源时钟和 Responses 回执保存在同目录的 `metrics/`。CPU 的 100% 表示一颗逻辑核；内存曲线使用整个 cgroup 的 memory.current，含文件页缓存。
